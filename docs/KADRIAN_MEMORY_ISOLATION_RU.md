# Изолированный канал памяти: подготовка, без установки

19.11.2026. Эта архитектура заменяет прежний план установки endpoint в общий Instagram/VK-сервер. Рабочие службы, Supabase, main и параметры Render не изменяются.

## Архитектура

Mac Kadrian (Keychain + зашифрованная очередь) → HTTPS → отдельный процесс `agent_memory_server:runtime_app` → существующие таблицы agent_memory_workspaces/revisions и RPC agent_memory_commit PR №85 в Supabase.

У процесса только три маршрута: /health, /ready и /memory-sync/v1/exchange. Нет Instagram/VK/OAuth маршрутов, lifespan, планировщика, восстановления подписок, catch-up, видеочереди, OpenAI или генераторов. /health показывает живой процесс без доступа к базе; /ready делает ограниченное чтение существующей памяти. Ни один старт не создаёт схему и не отправляет сообщения.

Связь с content_factory_oauth.py удалена, его содержимое совпадает с установленным базовым ed84e85. Общие функции хранения PR №85 переиспользованы, второе хранилище знаний не создаётся. Полный ключ Supabase остаётся только на доверенном сервере. MemoryOnlySupabaseStore дополнительно ограничивает исходящие операции: чтение идентичности одного проекта, чтение его памяти и общих утверждённых правил через DeviceService, запись только в project RPC. Jobs/connections/media и изменение общих правил запрещены. Это защита приложения, не отдельная ограниченная роль БД: существующий серверный ключ всё ещё привилегирован, его выдача новому процессу требует согласованной установки.

Сервер привязывается ровно к одному владельцу/агенту/проекту. Регистрация устройства с любой другой областью блокирует запуск. Подпись Ed25519, сроки запросов, стабильные event_id, CAS и сохранение конфликтов наследуются из PR №90. Клиент не получает ключ базы и не может выбрать другую область через тело запроса.

## Независимый выпуск

1. **PR №90 направляется в codex/memory-sync-integration, а не main.** Ветка создана от установленного ed84e85; действующие службы её не отслеживают. Сливать этот PR в main нельзя: существующий автодеплой main тогда всё ещё обновил бы службы.
2. Проверенный исходный commit экспортируется `tools/memory_sync_release.py build`. Builder использует `git show <точный SHA>:<allowlisted path>`, а не текущие изменённые файлы, и создаёт маленький каталог из семи Python-модулей, requirements.txt, .python-version и release.json с SHA-256. Клиентские файлы, .env, история переписки, медиа, handlers и worker entrypoints не входят.
3. После одобрения установки этот каталог можно опубликовать отдельным коммитом **только** в release/kadrian-memory-sync. В этой задаче публикация deploy-ветки и создание сервиса не выполняются. Нельзя передавать builder-вывод через merge в main. История исходников и старые release SHA сохраняются.
4. Новый выделенный сервис должен смотреть только на release/kadrian-memory-sync с **auto-deploy off**, без общих env groups и без диска. Установка/обновление выполняются вручную на точный release SHA после проверки манифеста; в CI нет deploy-hook/API-ключа Render и права развёртывания.
5. Перед выпуском `check-topology` получает свежий read-only список Render и актуальную базу PR. Он отклоняет main, общую ветку, а также любой посторонний сервис, привязанный к integration/release. Для уже созданного dedicated-сервиса нужен его точный ID. CI дополнительно блокирует небезопасную базу PR.

Защита действует при соблюдении этого маршрута. Владелец GitHub технически может вручную перенаправить PR обратно в main; это вне безопасного процесса. Новые repository rules/branch protection не устанавливались. Проверка исходного diff и актуальной топологии обязательна перед будущим выпуском.

## Проверки и границы доказательства

Искусственные тесты проверяют: запуск отдельного ASGI без импортов social/workers/providers и без стартового network I/O; отсутствие чужих маршрутов; round-trip с существующим Repository; отсутствие задания в очереди; невозможность обращения к другой области или jobs/connections/media; fail-closed конфигурацию; блокировку опасной топологии; сборку точного commit без непроверенных файлов/секретов и проверку манифеста.

Read-only снимки Render до/после подготовки фиксируют привязки веток, autoDeploy, suspended и обновления служб. Это вместе с отсутствием deploy-кода и изменением базы PR доказывает отделение ПОДГОТОВЛЕННОГО пути выпуска от действующего main. Живой эксперимент с обновлением production не проводился. Общие инфраструктурные ресурсы (Supabase, сеть, квоты workspace) остаются общими; абсолютную независимость от их сбоев не обещаем.

- Проверить окончательный PR/CI, точную базу integration и актуальную Render topology. Сливать только в integration после отдельного разрешения, не в main.
- Из проверенного source SHA собрать/проверить release artifact, сохранить старый release SHA; опубликовать только dedicated release branch.
- Получить выбор стоимости и разрешение на новый сервис. Создать только dedicated endpoint по service-plan.json (это проект спецификации, не отправленный API-запрос; plan=null намеренно требует выбора).
- Настроить только его собственные секреты/одну область/публичный ключ устройства; existing RLS/таблицы и ключи других служб не менять. Приватный ключ Mac — в Keychain. Не копировать общие env groups и ключи видеопровайдеров.
- Проверить /ready, безопасный round-trip, offline/replay/конфликт и актуальные правила, затем активировать локальные launchd/hooks по обновлённой инструкции. Пока нет отдельного разрешения, эти действия не выполнять.

## Откат

Остановить только локальный LaunchAgent и его два hook-обработчика с резервной копией; сохранить зашифрованную очередь. Отключить AGENCY_MEMORY_DEVICE_SYNC или отозвать устройство только на отдельном сервере. Вернуть предыдущий verified release SHA только этому сервису. Не откатывать main/сайт/социальные службы, не восстанавливать Supabase целиком, не удалять версии. Данные остаются в неизменяемой памяти PR №85. Backup версии 35 и все локальные журналы сохраняются.
