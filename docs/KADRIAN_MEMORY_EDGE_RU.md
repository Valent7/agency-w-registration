# Автоматическая память Кадриана через Supabase Edge Functions

Статус: подготовка отдельного выпуска. Установки нет. Никакие команды ниже не выполняются CI автоматически.

## Что сохраняется

Одна существующая память PR85: `agent_memory_workspaces`, `agent_memory_revisions`, `agent_memory_commit`. Новых таблиц, миграций, проектов Supabase, Render-сервисов, функций Неоны или видеозаданий нет. Полная история остаётся в Supabase. Старые backup, включая версию35, не изменяются.

Mac передаёт только изменения `context/PROJECT.md`, `DECISIONS.md`, `FEEDBACK.md` выбранной папки. Они записываются как неизменяемые legacy-события с неизвестной достоверностью. Это не автоматическое утверждение фактов или правил. Утверждённые облачные факты/решения и правила возвращаются в `context/SYNCED_MEMORY.md` — читаемую проекцию данных задачи. Исходные три журнала, Agent.md и AGENTS.md не перезаписываются. Общие правила в файлах меняет только владелец через отдельное утверждение. Облачные правила экспортируются только в статусе approved; контекст других клиентов исключён.

## Обмен и защита

1. Подготовленный launchd LaunchAgent запускает одноразовый клиент после входа в macOS, при изменении трёх файлов и каждые60секунд. До входа/разблокировки Keychain обмен недоступен. Пока Mac выключен, облачная память сохраняется существующим облачным агентом независимо от Mac.
2. Проектные Codex SessionStart/UserPromptSubmit hooks проверяют актуальность. Успешные проверки моложе60секунд объединяются. При недоступности памяти выводится предупреждение, работа с доступными локальными данными возможна.
3. Ed25519-ключ устройства хранится в Mac Keychain, WhenUnlockedThisDeviceOnly. Подписываются вся область owner/agent/workspace/project, операция, время, nonce и полезная нагрузка. Время допуска ±300секунд; часы Mac должны быть верны. Сервер выбирает область из доверенного реестра, сравнивает с единственным пилотом и проверяет подпись до любых запросов к БД.
4. HTTPS строго на `<project-ref>.supabase.co/functions/v1/kadrian-memory-sync`, без редиректов, proxy environment, секретов в URL/аргументах. На Mac нет service-role/Management API ключа Supabase.
5. На Edge используется встроенный серверный `SUPABASE_SERVICE_ROLE_KEY`. Это привилегированная доверенная граница: ключ сам по себе не ограничен RLS. Адаптер разрешает только чтение памяти трёх относящихся областей, проверку владельца проекта и запись в выбранный проект через существующий RPC. Устройство не может утвердить правило, изменить задачу или вызвать произвольный метод БД.
6. Новая функция требует точечно `verify_jwt=false`, поскольку проверяет подпись устройства вместо JWT. Это не разрешение анонимной записи: без валидной подписи нет обращения к БД. Настройки остальных функций не менять. Публичные ошибочные запросы всё равно могут расходовать Edge invocations; клиентский ограничитель не защищает организационную квоту от внешнего злоупотребления.
7. Временная очередь и базовый снимок на Mac зашифрованы, права каталогов0700/файлов0600, атомарная запись/fsync и блокировка процесса. Это транспортный кэш существующей памяти, не второе хранилище знаний. Потеря/порча кэша не вызывает его молчаливого удаления или повторной регистрации устройства.

## Версии, конфликты, история

Пустой обмен: один подписанный запрос, только `revision,hash` из БД, короткий ответ без документа, без записи в БД. Одна такая проверка выполняет семь небольших индексированных REST-чтений (принадлежность проекта, bindings и метаданные трёх областей); это около302400 чтений за30дней одного постоянно включённого Mac. Нагрузка и квоты БД остаются общими. При изменениях возвращаются новые снимки и approved-правила. Дельты журналов отправляются по одному событию на запрос, максимум три события за цикл; оставшаяся очередь отправится позже.

Существующие хеши вычислялись Python. JS не должен преобразовывать старые float/bigint. Клиент передаёт каноническое строковое представление уже проверенного базового документа; Edge проверяет SHA256 по хешу БД и вставляет только новую запись, сохраняя старые JSON-числа побайтно. В RPC документ и в ответе старый снимок передаются как raw JSON без повторной сериализации JS.

У события постоянные device+sequence+event_id; сетевой nonce не создаёт новую запись. Потеря ответа после успешной транзакции сверяется по неизменяемому событию. Повтор с другим содержимым отклоняется. CAS защищает параллельные изменения. При устаревшем основании сначала получается новый снимок, затем сохраняется новое отдельное событие с conflict=true; исходные данные не затираются, локальная конфликтная версия остаётся зашифрованной. Откат ревизии/пропажа родительских правил блокируют обмен.

При отсутствии сети очередь фиксируется ДО отправки. Повторные попытки через60секунд с увеличением до1часа; задержка переживает перезапуск. После восстановления сети/входа обмен продолжится в пределах сохранённой задержки. Не обещать немедленного восстановления при ещё действующем backoff. Порог документа на Edge1,6MB оставляет запас под существующий лимит RPC2MB; при достижении очередь сохраняется и требуется отдельное решение об архивировании. История автоматически не удаляется.

## Квоты и стоимость

Расчёт: 43 200 idle-запросов за30суток непрерывно включённого Mac (2,16% от2млн Pro), плюс изменившиеся данные/повторы/первичная загрузка. При10часах в день18 000 запросов. Короткий ответ около1KiB означает около0,044GB/30суток до Mac, плюс меняющиеся снимки и DB↔Edge. Это оценка, не счёт и не hosted-бенчмарк.

В существующей Pro-подписке включено2млн Edge invocations/месяц; дополнительная ежемесячная подписка не требуется. Сверх включённой квоты официальная цена$2/млн при разрешённом перерасходе; общий egress тоже ограничен тарифом. Существующий Pro и другие службы продолжают оплачиваться. Spend Cap сохранять включённым. Общие квоты/доступность Supabase разделяются с остальными приложениями даже при изолированном коде.

Клиент автоматически ведёт зашифрованный счётчик своего расхода за календарный UTC-месяц: по умолчанию100000 запросов/1GB ответов. Предупреждение с80%, точная доля в status.json; при пределе пауза с сохранением очереди. Перед отправкой резервируются запрос и максимальные3MB ответа: при сбое/выключении оценка остаётся консервативно завышенной, чтобы не потерять расход. Этот период отличается от биллингового цикла Supabase. Backoff и объединение частых hooks уменьшают нагрузку.

Реальный общий Billing / Usage автоматически не читается: для этого потребовался бы отдельный привилегированный организационный доступ. Не маскировать локальные счётчики под живые данные организации. Опциональная operator-observation `quota` в KADRIAN_MEMSYNC_CONFIG содержит observed_at, period_end, invocations, included_invocations, egress_bytes, included_egress_bytes (Unix seconds / целые байты). Снимок старше24ч/после конца периода маркируется unknown_or_stale; свежий расход≥80% предупреждение, ≥95%critical. До установки оператор проверяет Dashboard и запас общих квот; затем периодически обновляет наблюдение или согласует отдельный read-only мониторинг. При stale выводится честное предупреждение. Автоматического увеличения тарифа/Spend Cap/покупок нет.

Источники: [цена](https://supabase.com/docs/guides/functions/pricing), [лимиты](https://supabase.com/docs/guides/functions/limits), [auth](https://supabase.com/docs/guides/functions/auth), [Spend Cap](https://supabase.com/docs/guides/platform/cost-control).

## Отключение и откат

В отдельной настройке функции выключить enabled или отозвать конкретное устройство; остальные функции/сервисы не менять. На Mac выгрузить только `com.agency-w.kadrian-memory-sync` через launchctl bootout (GUI uid), восстановить сохранённые проектные hooks. Не удалять очередь, Keychain, историю, исходные файлы, backup или облачную35. Остановка клиента сохраняет pending для продолжения.

При ошибке версии развернуть прежние три файла этой же функции из проверенного артефакта; на Mac вернуть предыдущий code/config с сохранением транспортной очереди. Если старый клиент не понимает новый backend, оставить обмен выключенным и не подключать его к старому общему OAuth-сервису. Откат БД не нужен: схема не менялась, новая память только добавляла события. Исправлять ошибочные записи новым компенсирующим событием/явным владельческим откатом через существующие средства PR85; не удалять ревизии. Другие агенты продолжают работать.
