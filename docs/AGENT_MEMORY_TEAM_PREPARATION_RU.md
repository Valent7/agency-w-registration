# Подготовка общей памяти команды

Дата проверки — 20.11.2026. База — main 384630e. Этап — подготовка адаптера,
инвентаризация и синтетические проверки. Включение требует решения директора.

## Единый источник

Авторские AGENCY_W_CORE.md, docs/NEONA_CORE_V4_REFERENCE.md,
NEONA_KNOWLEDGE_BASE.txt и правила публичного входа сохраняют свой приоритет.
Память использует существующие Memory, Repository, таблицы ревизий и цикл
проверки и утверждения правил из PR85.

agent_memory_team.py предоставляет один адаптер для следующих профессиональных
ролей. Действующие обработчики ещё должны получить проверенную привязку к
проекту перед подключением. Этот модуль пока используется только тестами.

У каждого ряда подготовлен отдельный role ID. Каждый использует тот же
TeamMemory.context для чтения и TeamMemory.record_outcome для добавления.
Профессиональная инструкция агента остаётся у его действующего обработчика.
Записи памяти передаются модели как данные с границами доверия.
Готовность Кадриана относится к его существующему контуру; роли kadrian в новом
адаптере нет.

## Права и изоляция

- Все grants по умолчанию пусты. Существующие переменные включения Кадриана
  не предоставляют доступ новым ролям.
- Разрешение задаётся точной тройкой owner_id, agent_id, canonical project UUID.
  Владелец партнёрского кабинета является owner_id своей области.
- Идентичность владельца, проект и grants формирует доверенный сервер после
  действующей авторизации. Параметры URL, ответы модели и импортированные файлы
  для этого не подходят. Python Binding служит внутренним описанием привязки.
- Перед каждым чтением/записью вызывается access_check и проверяется принадлежность
  проекта через существующий store.get_project. При отказе операция останавливается.
- Запись ограничена своей областью роли/проекта. Каналы Неоны имеют разные role ID.
- Чтение общих правил владельца требует отдельного read_shared_rules=true.
  Наследуются только approved rules. Частные заметки других ролей и проектов
  в общий контекст не включаются.
- Ора всегда использует отдельный профиль проекта без наследования общих правил
  Агентства. Для реального включения нужен подтверждённый проект Оры.
- Перед production требуется определить реальный project UUID каждого агента:
  многие текущие диалоги привязаны к владельцу и контакту без проекта content factory.
  Создание или миграция таких привязок требует отдельного плана.

## Обратная связь и профессиональное обучение

success сохраняется как execution, error как analysis, feedback как feedback,
correction как correction. Каждая запись содержит исходный текст и источник.
Статус достоверности по умолчанию unknown. Слово success в событии ещё требует
подтверждения результата по существующим правилам доказательств.

Проверенные результаты записываются доверенным проверяющим через существующий
Memory.record(kind=check, evidence=...), а утверждение правил выполняет владелец.
TeamMemory не предоставляет методов автоматического утверждения правил.
Предложения и замечания не становятся полномочиями агента.

Для повторной доставки приложение сохраняет стабильный event_id в своём
долговременном outbox до подтверждения записи. Повтор с тем же ID и содержимым
использует существующую идемпотентность. Изменённое содержимое под тем же ID
вызывает конфликт. Источник сохраняется после перезапуска. Каждый будущий
обработчик должен связать этот контракт со своим долговременным событием.

## Проверки и приёмка

Новые тесты используют существующий Repository с SQLite и синтетических
владельцев. Проверяются пустые grants, отсутствие серверной проверки,
поддельный владелец проекта, отзыв доступа, разные проекты с одинаковым
названием, изоляция ролей/каналов, утверждённые общие правила, отдельный профиль
Оры, отбрасывание секретов и стабильные event ID.

Повторная доставка одного события, в том числе параллельная, создаёт одну
ревизию. Сохранение четырёх видов результата проверяется после повторного
открытия хранилища. Отдельно запускаются существующие тесты ядра и rollout.

Живое чтение каждым агентом, права Supabase, транзакционный отзыв разрешений
при конкурентных запросах и работа каждого канального outbox требуют отдельной
приёмки перед активацией. SQLite-проверка сама по себе не подтверждает production.
Нужен также просмотр итоговых CI-проверок на опубликованном коммите.

## Решения перед внедрением

1. Выбрать пилотную роль, владельца и существующий проект.
2. Согласовать состав сохраняемых данных и правила обезличивания, особенно
   для публичных посетителей и личных диалогов.
3. Проверить текущие серверные разрешения и привязки проекта.
4. Подготовить канальный outbox, приёмку Supabase и сценарий отзыва доступа.
5. Отдельно разрешить конкретное подключение. Межагентное копирование данных
   и автоматическое распространение новых правил требуют отдельного решения.
6. Согласовать изменение описания PR92 по результатам Mac-аудита.
7. Решить интервал подготовки к встрече 1ч/2ч. Данный этап только фиксирует вопрос.

## Затраты

Адаптер использует существующий серверный store. Каждый вызов проверяет
принадлежность проекта и читает свою область; общие правила добавляют ещё одно
чтение памяти. Каждое новое событие добавляет ревизию существующим механизмом.
Дополнительных LLM-вызовов или платных сервисов адаптер не создаёт. Возможный
расход БД и рост контекста зависят от числа событий и разрешённых правил.
Оценка по реальному объёму нужна перед массовым включением.

## Результат локального запуска

В отдельном временном Python3.12-окружении команда
python -m unittest discover -s tests -p 'test_agent_memory*.py' -q
завершилась успешно: 73 теста, из них 4 PostgreSQL-проверки пропущены.
Новые 16 тестов адаптера прошли. git diff --check также прошёл.
Доказательство текущих прав production Supabase и реального чтения знаний
работающими агентами остаётся отдельным этапом приёмки.
